## 1. هدف اصلی که در گفتگوها تعریف شد

این پروژه قرار بود پژوهش علمی تداخل آنتی‌بادی مادری و واکسن را به یک اپلیکیشن انتخاب‌محور تبدیل کند؛ به‌نحوی که کاربر بیماری و پلتفرم واکسن را انتخاب کند و مدل متناسب همان بیماری/محصول را ببیند. دامنه مورد انتظار شامل موارد زیر است:

- واکسن‌های زنده متعارف، غیرفعال، وکتوری/نوترکیب و چندظرفیتی؛
- واکسیناسیون جوجه‌کشی و بازه روز صفر تا هفته اول، در کنار برنامه‌های فارم؛
- تمایز MDA ضد آنتی‌ژن هدف از آنتی‌بادی ضد وکتور، و مسیرهای ارائه آنتی‌ژن/ایمنی سلولی؛
- تفکیک vaccine take، پاسخ سرولوژیک، ایمنی محافظتی، دفع ویروس و انتقال؛
- اثر سن، سویه، مسیر تجویز، دوز، نوع واکسن، کیفیت اجرا، یکنواختی گله و فشار عفونت؛
- مقایسه دوز استاندارد و دوز کمتر فقط در صورت وجود شواهد اختصاصی محصول و endpoint معتبر؛
- تکیه بر منابع مرجع، بروشور دقیق محصول و اعتبارسنجی میدانی، نه cutoff عمومی.

**نتیجه ممیزی دامنه:** نسخه فعلی فقط بخش محدودی از این هدف را پوشش می‌دهد. اپلیکیشن هنوز تصمیم‌یار جامع برای همه پلتفرم‌ها، بیماری‌ها، واکسن‌های جوجه‌کشی یا مقایسه دوز نیست.

## 3. وضعیت علمی مدل‌ها

### IBD — گامبورو

- محاسبه‌گر Deventer-style مقدماتی برای واکسن زنده متعارف در کد وجود دارد.
- ورودی‌ها شامل سن نمونه‌گیری، تیترها، BTT، نیمه‌عمر، درصد هدف، حداقل نمونه و اصلاح روزهای نخست است.
- کنترل‌های دستی QC، نمونه‌گیری تصادفی و تطابق assay/BTT به‌صورت gate وجود دارند.
- تحلیل حساسیت و تفسیر جداگانه برای دامپزشک/مرغدار وجود دارد.
- متن تفسیر اصلاح شده تا «رسیدن MDA به BTT» با «vaccine take»، «پاسخ ایمنی» و «حفاظت» اشتباه نشود.

**محدودیت‌ها:** فقط واکسن زنده متعارف؛ برای immune-complex، HVT‑VP2 یا سایر وکتورها قابل تعمیم نیست. BTT و نیمه‌عمر هنوز با انتخاب اجباری محصول/کیت از یک رکورد معتبر کنترل نمی‌شوند؛ بخشی از ورودی‌ها متن آزاد و تأیید دستی هستند. اعتبارسنجی مستقل prospective در گله‌های تجاری ایران انجام نشده است. راهنمای BioChek برای ۲۳ نمونه، راهنمای اختصاصی همان منبع است و قانون جهانی همه آزمون‌ها نیست.

### ND — نیوکاسل

- موتور پایش توصیفی HI بر حسب log2 وجود دارد.
- میانگین log2، GMT معادل، میانه، دامنه و در صورت ورود آستانه مستند، درصد responder گزارش می‌شود.
- مقایسه paired فقط با فرض همان پرندگان و همان ترتیب انجام می‌شود و هشدار این محدودیت نمایش داده می‌شود.

**هنوز وجود ندارد:** مدل افت MDA، مدل زمان‌بندی واکسن، مدل‌های جداگانه برای زنده/غیرفعال/وکتوری، مدل day‑old/hatchery، و پیش‌بینی حفاظت یا دفع ویروس.

### IBV — برونشیت عفونی

- موتور روند زمانی نتایج هم‌آزمون/هم‌واحد وجود دارد.
- محاسبه fold برای HI-log2 بر اساس اختلاف log2 و تبدیل به مقیاس reciprocal اصلاح شده است.

**هنوز وجود ندارد:** مدل MDA و زمان‌بندی، حفاظت مخاطی، cross-protection ژنوتیپی، و اتصال به PCR/typing و endpoint میدانی.

### AIV — آنفلوانزای پرندگان

- Evidence gate برای دسته‌بندی سیگنال‌ها و اولویت ارجاع وجود دارد.
- PCR مثبت، علائم یا افزایش تلفات به ارجاع فوری منجر می‌شود؛ سرولوژی به‌تنهایی تشخیص تلقی نمی‌شود.

**هنوز وجود ندارد:** مدل زمان‌بندی واکسن، DIVA عملیاتی/اعتبارسنجی‌شده، تطابق آنتی‌ژنی محاسباتی، و مدل انتقال/دفع ویروس.

### خلأ علمی مهم در کل برنامه

پژوهش روز ۱۶ نوامبر درباره تفاوت MDA ضد آنتی‌ژن هدف و آنتی‌بادی ضد وکتور، به‌ویژه تفاوت HVT با وکتورهای NDV/FPV، باید به یک ماتریس شواهد محصول‌محور و سپس مدل‌های جداگانه تبدیل شود. در حال حاضر این موضوع در اپلیکیشن محاسبه نمی‌شود. همین‌طور مقایسه دوز استاندارد با دوز کمتر، اقتصاد، یکنواختی گله و shedding هنوز موتور نرم‌افزاری ندارند.

## 4. آزمایشگاه، کیت و ورود داده

- رجیستری کد شامل کیت‌های مستند و catalog-only است و از تبدیل خودکار مقیاس کیت‌ها جلوگیری می‌کند.
- در دیتابیس ۱۰ رکورد assay و یک محصول واکسن ثبت شده است.
- محصول Avishield IBD Plus با BTT=500 فقط به‌عنوان برچسب بریتانیا (GB، June 2024، IDEXX 99-09260) ثبت شده؛ این به معنی مجوز یا موجودی در ایران نیست.
- قرارداد QC و provenance شامل lot، IFU، کنترل‌ها، reader، نرم‌افزار، OD خام و وضعیت‌های زیر LOD/بالای محدوده تعریف شده است.

**هنوز انجام نشده:** parser واقعی فایل BioChek II یا IDEXX xChekPlus، تطبیق خودکار خروجی نرم‌افزار با داده خام، golden files و اعتبارسنجی round-trip. فرم پایش ND/IBV/AIV نیز هنوز داده را ذخیره نمی‌کند.

## 5. وضعیت Supabase و امنیت

پروژه `Adine-Vaccine-Timing` در منطقه `eu-central-1` فعال و سالم است؛ PostgreSQL 17.12.

جداول موجود:
- `diseases`
- `assay_kits`
- `vaccine_products`
- `flocks`
- `serology_batches`
- `serology_results`
- `model_runs`

هر هفت جدول RLS فعال دارند. سیاست‌های مالکیت با `auth.uid()` تعریف شده‌اند و برای رکوردهای فرزند، مالکیت گله/سری آزمایش مرجع نیز کنترل می‌شود. بررسی Security Advisor در زمان ممیزی finding امنیتی گزارش نکرد؛ Health Advisor نیز finding نداشت. ۱۳ شاخص به‌عنوان unused گزارش شدند که با توجه به خالی بودن جدول‌های عملیاتی، فعلاً دلیل حذف آن‌ها نیست.

وضعیت داده‌ها در زمان ممیزی: ۴ بیماری، ۱۰ assay، یک محصول واکسن؛ جدول‌های گله، سری آزمایش، نتایج و اجرای مدل هنوز رکورد عملیاتی ندارند.

**فاصله اصلی:** در `package.json` وابستگی `@supabase/supabase-js` وجود ندارد؛ هیچ client یا جریان Auth/CRUD/sync در رابط برنامه پیاده‌سازی نشده است. `.env.example` فقط جای URL و کلید عمومی را آماده کرده است. فایل TypeScript دیتابیس از schema فعلی Supabase دوباره تولید و همگام شده، اما تا زمان اتصال client استفاده عملیاتی ندارد.

**قبل از اتصال:** باید تنظیمات Data API و exposed schema برای پروژه جدید بررسی شود؛ اعطای GRANT و فعال بودن RLS به‌تنهایی تضمین نمی‌کند جدول‌های تازه‌ساخته‌شده از Data API قابل دسترسی باشند.

## 6. مهاجرت‌های دیتابیس و بازتولیدپذیری

نام فایل‌های migration در شاخه با نسخه‌های ثبت‌شده در تاریخچه remote هم‌تراز شد. ۹ migration موجود با تاریخچه فعلی remote منطبق‌اند؛ یک migration تکمیلی برای همسان‌سازی metadata منبع CK113 بعد از آن قرار دارد. SQL مربوط به سیاست مالکیت فرزند نیز از نظر پرانتزهای ناقص اصلاح شد.

**موارد باقی‌مانده:** هنوز اجرای کامل migrationها از یک دیتابیس خالی و مقایسه schema حاصل با پروژه remote در CI انجام نشده است. فایل `supabase/config.toml` و `package-lock.json` در مخزن وجود ندارند؛ بنابراین محیط محلی/وابستگی‌های ترانزیتی هنوز کاملاً reproducible نیستند. پیش از هر `db push` باید وضعیت migration history و Data API دوباره بررسی شود؛ هیچ migration جدیدی در این ممیزی به دیتابیس remote اعمال نشد.

## 7. آفلاین، ذخیره‌سازی و امنیت داده

- پوسته برنامه پس از بارگذاری آنلاین اولیه cache می‌شود.
- پروفایل و تحلیل IBD روی همان مرورگر در localStorage ذخیره می‌شوند.
- پشتیبان JSON قابل export/import است و import به‌صورت merge انجام می‌شود.
- رمزنگاری داده‌های localStorage، ورود آفلاین مبتنی بر حساب، IndexedDB، صف عملیات آفلاین، background sync، تعارض‌زدایی چنددستگاهی و همگام‌سازی با Supabase پیاده‌سازی نشده‌اند.
- در نتیجه این نسخه برای داده‌های حساس فارم روی دستگاه مشترک یا برای کار چندکاربره آماده نیست.

## 9. اولویت‌های لازم پیش از انتشار

1. اتصال امن Supabase Auth و CRUD، با تست RLS چندکاربره و مالکیت parent-child.
2. طراحی local-first واقعی: IndexedDB، صف تغییرات، retry، conflict resolution و همگام‌سازی قابل مشاهده؛ بدون شکستن تجربه آفلاین.
3. اتصال انتخاب محصول/کیت دقیق به BTT، نسخه IFU، مقیاس و روش؛ حذف ورودی آزاد برای پارامترهای حساس محاسبه.
4. ساخت parser آزمایشگاه فقط پس از دریافت فایل‌های واقعی و مستند BioChek/IDEXX.
5. تکمیل ماتریس MDA برای واکسن‌های زنده، غیرفعال، immune-complex، HVT، NDV-vector و FPV-vector؛ تفکیک ضد وکتور/ضد آنتی‌ژن هدف.
6. طراحی مدل مستقل برای بیماری و پلتفرم؛ ابتدا پایش، سپس مدل زمان‌بندی فقط با داده کافی.
7. اعتبارسنجی prospective و مستقل با داده‌های سرولوژی، vaccine take، PCR/sequence، پاتولوژی/چالش و عملکرد گله؛ هر endpoint جداگانه.
8. افزودن تست SQL migration، تست end-to-end و آزمون واقعی PWA روی دستگاه.
9. پس از عبور از gateهای علمی، امنیتی و عملیاتی، بازبینی PR و سپس انتشار کنترل‌شده.

**جمع‌بندی:** پایه فنی MVP و اسکیمای اولیه دیتابیس ساخته شده و CI فعلی موفق است؛ اما محصول هنوز یک اپلیکیشن عملیاتی متصل به ابر یا تصمیم‌یار جامع علمی نیست. بزرگ‌ترین کارهای باقی‌مانده اتصال داده و حساب کاربری، آفلاین واقعی و همگام‌سازی، کنترل اجباری provenance کیت/واکسن، مدل‌های اختصاصی MDA/پلتفرم، parser آزمایشگاه و اعتبارسنجی میدانی هستند.
